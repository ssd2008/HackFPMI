# Как валидировать поиск по почте

**Версию для хакатона выбираем по nDCG@10 на новых запросах к корпусу организаторов.** На открытой части подбираем веса поиска и порог пустой выдачи. Финальную часть с эталонными ответами хранит другой участник команды. Он сравнивает на ней две зафиксированные версии — исходную и выбранную. Личные ящики покажут, помогает ли изменение в настоящей почте, а отдельный интернет-архив — как оно переносится на другой источник.

В TREC фиксируют корпус, запросы и оценки релевантности документов каждому запросу (*qrels*), затем сравнивают выдачи систем. В исследованиях поиска по личной почте также проверяют, нашёл ли человек конкретное письмо в своём ящике. [Методика TREC, NIST](https://trec.nist.gov/howto.html) · [Mackenzie и соавт., исследование поиска в личной почте](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/02/Mackenzie-www19.pdf)

## Открытые почтовые и внешние наборы

Сначала сравнили исходный MVP `5fe3f5d` и версию поиска и RAG `b37c309`, которая работала на момент получения новых данных. Границы календарных периодов и различие между предупреждением об отмене и её подтверждением исправили в `b5252c1`. Две эти ошибки нашли на открытых задачах. Повторный замер показывает эффект исправления на разработочном наборе. Оба личных ящика Кирилла и пять ящиков VK зарезервированы для однократной проверки после выбора финалиста. ### Поиск писем

Каждая версия получила один и тот же полный корпус соответствующего источника. В 16 376 синтетических письмах проверили 1 471 положительную задачу и 711 проверенных пустых. В объединённом корпусе из 9 366 личных писем открытые запросы приходятся на одного владельца, 1 815 положительных и 152 пустых. Варианты формулировок относятся к исходным задачам и учитываются отдельно. Первичную выдачу получили через штатный `POST /api/search`, затем повторили запросы фиксированных панелей независимо.

После исправления календарных формулировок в первой десятке осталось 1 901 письмо VK и 7 793 личных письма по основным запросам с ограничением по дате. Каждое возвращённое письмо попало в запрошенный период. При проверке всех 3 754 дополнительных формулировок нарушения периода также исчезли. Ни одна из трёх версий не показала писем другого ящика или писем, датированных позже самого запроса. На фиксированных панелях по 250 задач nDCG@10 вырос с 0,95621 до 0,97133 на VK и с 0,84199 до 0,89510 на личной почте. Для последнего изменения 95%-й парный интервал прироста nDCG@10 составил от +0,00283 до +0,01455 на VK и от +0,05118 до +0,07158 на личной почте. Повторные выборки формировали по семействам запросов, всего 1 219 и 620 семейств с положительными метками. Разметка включает исчерпывающие правила для точных условий, отдельно проверенные задания и неполные тематические оценки. Запросы второго владельца потребуются для оценки переноса между людьми.

В дополнительных парных задачах версии сравнивали по двум ответам сразу. Предупреждение о возможной отмене должно находиться по запросу о риске, а при запросе подтверждения произошедшей отмены выдача должна быть пустой. Результат вырос с 0/14 до 14/14 пар. Все версии прошли 24/24 пары о письме с неизвестной датой получения. Для диагностики использовали только семь открытых ящиков VK. Остальные 18 пар сохранены до финального замера. На 99 публичных запросах VK у двух последних версий совпал порядок всех писем в первой десятке. nDCG@10 составил 0,999051, Recall@10 достиг своего верхнего предела 0,937564. После прогрева в двух сериях с восемью одновременными клиентами серверный p99 составил 8,27–8,85 мс у `b5252c1` и 8,10–9,01 мс у `b37c309`. С одним клиентом диапазоны составили 3,50–3,60 мс и 3,26–3,67 мс соответственно. Всего проверили 3 960 вызовов через HTTP с чередованием порядка версий. ### Ответы с цитатами

Через `/api/answer` задали все 315 открытых вопросов из отдельной RAG-разметки, каждый со своим ящиком и датой. Оценивали требуемый факт, посторонние утверждения и привязку каждой цитаты к оригиналу. В синтетической почте из 246 вопросов с ответом 242 построены по одному шаблону о сумме заказа. Оставшиеся четыре естественных вопроса VK и один личный дают лишь несколько примеров качества живого диалога.

В двух последовательных повторах каждого вопроса обе версии вернули одинаковые тексты и ссылки во всех восьми сравнениях. ### Как повторить

Команды ниже запускаются из репозитория с установленными зависимостями и локальными весами. В переменной `POOL` укажите каталог полученного пакета с подкаталогами `suite`, `panels`, `rag`, `diagnostics` и `external/benchmarks`. Исходные документы, вопросы из личной почты и сохранённые тексты ответов используются локально. Для сверки опубликованной разметки нужна ветка команды `codex/ood-validation-pool`.

```sh
POOL="$HOME/Downloads/HackFPMI-mail-OOD"
git fetch origin codex/ood-validation-pool
```

Для сравнения двух последних версий запустите по две локальные копии API из рабочих деревьев `b37c309` и `b5252c1`. Каждая принимает `--data "$POOL/suite/vk_dev"` либо `--data "$POOL/suite/personal_dev"` и отдельный `--port`. В примере VK использует порты 18782 и 18780, личная почта 18776 и 18781.

```sh
.venv/bin/python tools/check_mail_ood.py --pool "$POOL" --run \
  --baseline-revision b37c309 --candidate-revision b5252c1 \
  --vk-dev-before http://127.0.0.1:18782 --vk-dev-after http://127.0.0.1:18780 \
  --personal-dev-before http://127.0.0.1:18776 --personal-dev-after http://127.0.0.1:18781 \
  --runs .cache/recheck-mail --output .cache/recheck-mail/search.json
.venv/bin/python tools/check_ood_pairs.py --pool "$POOL" \
  --baseline-revision b37c309 --current-revision b5252c1 \
  --baseline-url http://127.0.0.1:18782 --current-url http://127.0.0.1:18780 \
  --output .cache/recheck-mail/pairs.json
.venv/bin/python tools/check_mail_ood_rag.py --pool "$POOL" \
  --baseline-revision b37c309 --candidate-revision b5252c1 \
  --vk-before http://127.0.0.1:18782 --vk-after http://127.0.0.1:18780 \
  --personal-before http://127.0.0.1:18776 --personal-after http://127.0.0.1:18781 \
  --cache .cache/recheck-mail/rag --output .cache/recheck-mail/answers.json
```

Внешним тестам достаточно двух коммитов в локальной истории и подготовленных снимков. Каждый запуск использует штатный метод поиска в отдельном процессе. Время на построение индексов и разметка не входят в показатели интерактивного сервиса.

```sh
.venv/bin/python tools/check_ood_transfer.py --benchmarks "$POOL/external/benchmarks" \
  --datasets beir-scifact enron-mail rubq-2.0 mr-tydi-ru miracl-ru mmarco-ru msmarco-passage msmarco-doc lotte \
  --baseline-revision b37c309 --current-revision b5252c1 \
  --cache .cache/recheck-transfer --output .cache/recheck-transfer/results.json
```

## Решение по первым 12 новым задачам VK

По этому пилоту сохраняем исходную версию для командного демо. В закрытой половине разница nDCG@10 между кандидатом и исходным MVP составила **−0,00299**, 95%-й интервал — от −0,03817 до +0,02920. Одна задача улучшилась, три дали одинаковый результат, одна ухудшилась. Пять положительных задач в трёх ящиках оставляют заметную неопределённость. [Парное сравнение по половинам](results/grouped_vk_pilot.json)

| Проверка | Исходный MVP `5fe3f5d` | Кандидат `7897913` |
| --- | ---: | ---: |
| Открытая половина, nDCG@10 по 5 положительным задачам | 1,00000 | 1,00000 |
| Закрытая половина, nDCG@10 по 5 положительным задачам | 0,82461 | 0,82162 |
| Закрытая половина, Recall@10 | 0,60857 | 0,59905 |
| Целевое письмо на первом месте, обе половины | 5 из 5 | 5 из 5 |
| Верная пустая выдача, обе половины | 1 из 2 | 1 из 2 |

На запрос о посадочном QR-коде на паром в явно указанную дату исходная версия показала одно постороннее письмо, кандидат — десять. Обе верно вернули пустую выдачу для отсутствующего номера заказа. Проверка всех 89 и 98 возвращённых писем соответственно не выявила нарушений ящика и даты. На закрытых задачах у кандидата в первые 50 предварительных результатов попало в среднем 75,33% известных релевантных писем, в первые 128 — 83,33%, в финальную десятку — 59,90%. На отдельном сравнении с тем же фильтром дат поиск по словам BM25 получил nDCG@10 0,86834, векторный E5 — 0,34281. [Проверка доступа](results/validation_pilot/scope-audit.json) · [Отбор кандидатов](results/candidate_recall_pilot.json) · [Выдачи сравниваемых методов](results/validation_pilot/pool-origins.json)

До первого обращения к поиску зафиксировали тексты, критерии и оценки для пяти конкретных писем, пяти подборок и двух пустых запросов. Два ящика целиком выделили на открытую часть, три других — на закрытую. Ни одного из пяти нет в публичных 99 запросах. Четыре ящика встречались в прежних технических проверках по другим событиям. Новые цели, положительные ID и тексты писем проверили на пересечения с прежними целями. Разметку выставил агент по правилам для 16 305 допустимых пар «запрос — письмо». Правила нашли 49 релевантных писем, включая три, которые пропустили все четыре поисковых метода. Команда может пересмотреть присвоенные оценки по сохранённым критериям. У одной неоднозначной карточки товара понижение оценки с 2 до 1 меняет закрытую разницу до −0,00183. | Дополнительная почта | В `data/Kirill-mails.jsonl` есть 2 467 писем Gmail и 960 из частичной выгрузки Яндекса. В `data/Sergey-mails.jsonl` — 5 939 писем и 5 099 различных `thread_id`. Публичные qrels относятся к другому корпусу. | Снимки зафиксированы. Есть технические проверки и отдельные бланки для собственных запросов владельцев. |

## Как собрать внутренний тест

Рабочая цель — **120 новых поисковых задач**, по 60 на корпусе VK и на личной почте. Задача — то, что человеку нужно найти в конкретном ящике на конкретную дату. Опечатка или перефразировка той же мысли остаётся вариантом одной задачи. Начать можно с 24 задач, по 12 на каждом источнике. Заранее отложить около половины целыми группами. Этот пилот даст оценку трудозатрат и покажет крупные ошибки. При расширении набора закрытую часть можно сохранить для финального прогона.

| Источник | Для разработки | Для однократной проверки |
| --- | --- | --- |
| Корпус VK, новые задачи | Около 40. Включить запросы без дня, с периодом, по отправителю, номеру, теме и статусу. | Около 20. Взять новые цепочки и темы, задействовать в том числе пять ящиков без публичных запросов. Предварительно отметить ящики и темы, которые уже использовались в ручных проверках. |
| Личные ящики команды | Около 40. Владелец записывает естественный запрос по памяти до просмотра подсказок системы, затем сам находит нужное письмо и подтверждает цель. | Около 20. Из двух владельцев отложить целиком того, чьи запросы ещё не использовались для настройки. Gmail и Яндекс одного человека считать одним владельцем и двумя ящиками. Если запросы обоих уже влияли на поиск, оценивать новые задачи знакомых владельцев и так подписать результат. |
| Собранные интернет-данные | Записать источник, версию и язык, проверить импорт. Если есть готовые qrels, установить, что считается документом и подходят ли оценки для поисковой задачи. | Отдельный тест переноса, ориентир ещё 20 задач или весь подходящий тест источника. При нескольких архивах целиком отложить один. Для корпуса без готовых запросов разметить задачи по процедуре ниже. До этого на нём можно измерять скорость. Для архива без естественных ящиков область поиска — вся коллекция. [Подход BEIR к сравнению доменов](https://arxiv.org/abs/2104.08663) |

На каждые десять новых задач ориентир — четыре поиска конкретного письма, четыре подборки нескольких писем и два случая с подтверждённым отсутствием совпадения. Это состав теста, а доли реального трафика пока неизвестны. Среди положительных задач предусмотреть вопросы о сумме, сроке или статусе. Для части вопросов подобрать ситуацию, когда тематическое письмо есть, но требуемый факт в нём отсутствует.

**Разметка одного запроса**

1. Записать текст, ящик, `query_date`, цель и критерий успеха до просмотра результатов сравниваемых систем. Например, «Найди письмо, в котором перенесли срок оплаты счёта». Уведомление о выставлении того же счёта — правдоподобная ошибка. Для задачи о новом сроке сохранить также эталонную дату и фрагмент письма, где перенос подтверждён.
2. Собрать и перемешать уникальные письма из первых 10 результатов BM25, E5 и текущего гибрида. Добавить известную владельцу цель, близкие ошибочные совпадения и несколько писем, найденных независимым способом, например просмотром переписки по отправителю. Для широких подборок углубить пул до 20 на систему или просмотреть всё небольшое допустимое окно. Разметчику показывать запрос и письмо, скрывая название системы и ранг. [Объединение выдач и ограничения неполной разметки, NIST](https://tsapps.nist.gov/publication/get_pdf.cfm?pub_id=934130)
3. Для собственных qrels использовать оценки **2** — целевое письмо или прямое свидетельство, **1** — полезный контекст, **0** — проверенное нерелевантное письмо. Отсутствующая оценка означает «не просмотрено». Повторно разметить вслепую примерно 20% запросов вторым человеком, которому доступны соответствующие письма. Записать долю совпадений по оценкам, разобрать расхождения и зафиксировать итог. Закрытую личную переписку может подтверждать сам владелец. Общему отчёту достаточно обезличенных ID и агрегатов.
4. Различать три состояния поиска — `positive`, `verified_empty`, `unjudged`. Пустой пул ещё не доказывает отсутствие письма. Для `verified_empty` нужен исчерпывающий просмотр доступного небольшого окна или проверяемое условие, например отсутствие точного номера во всём снимке ящика. Для частичной выгрузки вывод относится только к её снимку. Для RAG отдельно фиксировать, достаточно ли сведений для ответа.
5. Проверить покрытие разметки. На собственных положительных задачах считать долю вручную оценённых писем среди фактически возвращённых в top‑10 (*Judged@10*), рядом указывать длину выдачи. Пустая выдача даёт пропуск этой метрики. Перед сравнением финалистов оценить все новые письма из top‑10 обеих замороженных версий, скрыв их происхождение, и пересчитать обе на одних qrels. Recall при неполном пуле означает полноту по **известным** релевантным письмам. На публичном dev следовать правилу организаторов, где отсутствующая пара получает 0 при подсчёте.

Для запуска достаточно двух совместимых с проектом таблиц. В файле запросов нужны `query_id, synthetic_user, query, query_date`, в qrels — `query_id, doc_id, relevance`. Состояние разметки, целевые ID для поиска конкретного письма, эталонный факт и подтверждающий фрагмент хранить отдельно с тем же `query_id`. Так пустой результат можно оценить, даже когда для запроса нет положительных строк в qrels.

## Как делить данные и где применять KFold

**Сначала отложить закрытые задачи, потом настраивать поиск.** В таблице разбиения оставить `query_id` каждой формулировки, общий `family_id` вариантов одной задачи, источник, владельца, ящик, цепочку, сценарий, дату и назначение `dev / blind`. Перед разбиением объединить задачи с одной цепочкой, одним заказом, целевым письмом или его пересланной копией. Проверить пересечение открытой и закрытой частей по этим группам, в том числе по отпечаткам копий письма в разных архивах.

| Что хотим узнать | Как проверить |
| --- | --- |
| Какие веса гибрида, порог отказа или вариант переранжирования выбрать | На открытой части использовать `GroupKFold` с 5 фолдами по независимым группам задач. При малом числе групп и пустых срезах перейти на 3 фолда или фиксированную групповую отсечку. Настраивать обучаемые компоненты на остальных фолдах, оценивать на оставшемся. Для каждой конфигурации собрать по одному отложенному прогнозу на задачу, затем сравнить конфигурации. Для полностью фиксированных BM25 и E5 достаточно один раз сохранить выдачи и оценить их на тех же группах. [Групповая кросс-валидация](https://scikit-learn.org/stable/modules/cross_validation.html#cross-validation-iterators-for-grouped-data) |
| Работает ли поиск для нового владельца или новой темы | При достаточном числе владельцев брать `owner_id` ключом группировки. Дополнительная проверка — по очереди исключать одного владельца либо один целый тематический шаблон из всех настроек. Семь ящиков публичного dev дают семь диагностических срезов, в двух из них лишь один и два запроса. При одном-двух реальных владельцах показывать каждого отдельно. Проверка по цепочкам внутри ящика характеризует новые задачи этого владельца. |
| Как поиск ведёт себя со временем | Выбрать границу по `query_date`. Настраивать на ранних задачах, проверять на поздних. Группу, пересекающую границу, исключить из настройки и оценивать только её поздние запросы. «Вчера» отсчитывать от `query_date`. В своём ящике пользователь видит письма с известной датой не позднее дня запроса. MVP допускает `doc_dt=null` в обычном поиске и исключает такие письма при явном фильтре по дате получения. Для строгого исторического теста рассчитывать IDF, словари и другие статистики по доступному на тот момент снимку. |
| Переносится ли улучшение на действительно новую проверку | Участник, который хранит blind, запускает исходную и выбранную версии после фиксации обеих конфигураций. До этого разработчикам доступны правила разметки и размеры срезов. После разбора ошибок раскрытые задачи переходят в регрессионный набор, для следующего независимого вывода собирается новая порция. |

Письма, в которых предстоит искать, входят в индекс соответствующего ящика и снимка. До разметки дат зафиксировать часовой пояс источника. При импорте одного архива перевод из UTC в московское время изменил календарный день 263 писем. [Проверка импорта](results/additional_corpora.json)

Метки и вопросы отложенной части исключаются из обучения, подбора синонимов, порогов и примеров для RAG. Оценка победителя на использованных для выбора фолдах остаётся оценкой разработки. [Почему выбор модели и итоговая оценка требуют разных данных](https://scikit-learn.org/stable/auto_examples/model_selection/plot_nested_cross_validation_iris.html)

## Что измерять

| Вопрос | Метрика и знаменатель |
| --- | --- |
| Хорошо ли упорядочены первые письма? | **nDCG@10** на запросах с положительной разметкой. Внутри запроса выигрыш письма равен `2^relevance − 1`, вклад на позиции `i` делится на `log2(i + 1)`, затем сумма нормируется на идеальный top‑10. Главный показатель — среднее по исходным новым задачам VK. Личные ящики и интернет оцениваются отдельными строками. |
| Может ли человек сразу открыть конкретное письмо? | **Success@1** и **Success@5** — доля задач поиска конкретного письма, где целевой ID попал на первое место или в первую пятёрку. **MRR@10** — среднее `1 / ранг` первого допустимого целевого ID, промах даёт 0. Допустимые копии заранее перечисляет разметчик. Для совместимости отдельно воспроизводим публичный MRR по 42 запросам с одной положительной меткой. |
| Где теряются письма из подборки? | **Recall@10** — найденные положительные ID среди первых десяти, делённые на все известные положительные ID запроса. Для этой метрики положительны оценки 1 и 2. **Candidate Recall@50** — та же доля в списке до переранжирования, при бюджете 50 кандидатов. Для неё нужно сохранить выход первого этапа. Пара этих значений различает потери при отборе и при формировании первой страницы. |
| Когда поиск предлагает лишнее или промолчит? | **Ложная выдача** — доля `verified_empty` с хотя бы одним возвращённым письмом. **Ложная пустота** — доля `positive` с пустой выдачей. Порог выбираем по обеим долям только на dev. `unjudged` учитываем как объём ещё неразмеченных запросов. |
| Сохраняется ли смысл при другой формулировке? | Парная разница **nDCG@10(вариант) − nDCG@10(исходный)** на тех же положительных задачах, отдельно для перефраз и опечаток. Для противоположных статусов считать долю пар, где обе выдачи на первом месте показывают правильный статус. Удаление «вчера» расширяет область поиска и требует новых qrels. До переразметки такие запросы годятся для проверки скорости и области доступа. |
| Соблюдаются ли ограничения ящика и времени? | Число чужих, будущих и выходящих за явное окно получения писем в выдаче и в источниках ответа. Отдельно проверить открытие оригинала по прямому ID с чужим ящиком или более ранней датой. Для каждого типа указывать число нарушений и проверок. Внутреннее условие выпуска — **0 нарушений**. Дата мероприятия или срок оплаты внутри текста имеют иной смысл, чем дата получения. |

Для основного среднего берём одну исходную формулировку на задачу. По каждому источнику и сценарию показываем число задач, число ящиков и результат. По личной почте приводим также среднее с равным весом владельцев. При пустом срезе ставим «нет данных».

### Ответы RAG

Для каждого размеченного вопроса сохранить обязательные факты, допустимые варианты написания, ID писем и подтверждающие фрагменты. Для сумм сверять число и валюту, для дат — календарное значение, для статусов — объект и исход операции. Один и тот же вопрос прогнать через обычный `/api/answer` и, при диагностике, подать генератору эталонные фрагменты. Если на эталонных фрагментах ответ верен, искать потерю в поиске или выборе контекста.

- **Правильный ответ с подтверждением** — доля вопросов с достаточными сведениями, где даны все обязательные факты, нет противоречащих утверждений и для фактов открываются подтверждающие письма. Отказ на таком вопросе даёт 0.
- **Качество ссылок.** Точность — доля ссылок, которые сами подтверждают утверждение или дают необходимую часть совместного доказательства. Полнота — доля фактических утверждений ответа, подтверждённых указанными письмами. Каждая ссылка должна открывать оригинал в том же ящике на ту же дату. При нулевом знаменателе ставить прочерк и учитывать отказ в сквозной оценке. [ALCE, методика оценки цитирования](https://aclanthology.org/2023.emnlp-main.398/)
- **Ошибки отказа.** На вопросах с недостаточными сведениями считать долю ответов, в которых система всё-таки сообщает запрошенный факт. На вопросах с достаточными сведениями — долю необоснованных отказов. Отдельно показывать количество режимов `generative`, `extractive`, `no_evidence`. Корректная выдержка может решить задачу. Автоматическую оценку свободного текста стоит сверять со слепой ручной разметкой на местных примерах. [ARES, оценка компонентов RAG с человеческой разметкой](https://aclanthology.org/2024.naacl-long.20/)

### Задержка и пользовательская проверка

Сравнивать серверный p50/p95/**p99** по `Server-Timing` для `/api/search` на одной машине, одном снимке и при одинаковом `K=10`. Для каждой версии провести отдельные прогоны с 1 и 8 клиентами, заранее зафиксировать прогрев, порядок запросов, состояние кэша и одинаковую долю широких запросов без дня. Ориентир — от 1 000 вызовов на режим, повторить серию и показать разброс, число ошибок и тайм-аутов. После перезапуска отдельно записать время первого запроса. Поиск завершается готовой выдачей. Время `/api/answer` и полное время клиента идут в отдельные колонки. [Таймер сервера](mailsearch/app.py) · [Существующий нагрузочный прогон](results/public_dev_8_clients.json)

При наличии нескольких тестировщиков дать им реальные задачи по своей почте и скрыть название версии. Распределить сопоставимые задачи между A и B, поменять порядок версий у половины людей. Измерить долю задач с открытым правильным письмом, время до открытия и число переформулировок. Один участник решает каждую задачу впервые. Это проверяет, помогает ли улучшение выдачи в самом интерфейсе. [Исследование задач повторного поиска писем](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/02/Mackenzie-www19.pdf)

## Как принять решение

1. Зафиксировать базовую версию, снимки корпусов и qrels, разбиение, конфигурации и правила выбора до открытия blind. На dev сравнить хотя бы фильтр даты, BM25, E5 и рабочий гибрид с одинаковой областью доступных писем. Для закрытой проверки оставить базовую версию и одного кандидата.
2. Сравнить версии **попарно** на одних задачах. Вычислить разницу nDCG@10 и 95%-й интервал парным бутстрэпом. Сделать 10 000 выборок независимых групп с возвращением внутри источника, в каждой взять те же группы для A и B и пересчитать разницу средних. Границы — процентили 2,5 и 97,5. При достаточном числе владельцев сначала выбирать владельцев, затем группы внутри них. При одном-двух владельцах интервал по задачам условен для этих ящиков. Показать и простые числа побед, ничьих и поражений. Повторы замера времени и варианты одного запроса не увеличивают число независимых наблюдений. [Доверительные интервалы для поисковых метрик, NIST](https://www.nist.gov/publications/computing-confidence-intervals-common-ir-measures)
3. Для первой итерации предлагаем выбирать на dev по nDCG@10 новых задач VK среди версий с нулём нарушений доступа, p99 < 1 000 мс и без роста числа ложных выдач на проверенных пустых запросах. На blind проверить те же ограничения. Считать преимущество подтверждённым, если нижняя граница интервала прироста на новых задачах VK выше нуля. Для реальной почты заранее задать допустимое падение, например 0,02 nDCG@10. Тогда нижняя граница разницы «кандидат минус база» должна быть выше −0,02. При широком интервале оставить базовую версию и показать, какой диапазон изменений всё ещё совместим с данными. Для ошибок пустой выдачи и ответов RAG привести числители и знаменатели.

**Что можно запустить сейчас.** При запущенном из корня проекта `./run.sh` следующие команды сохранят публичные метрики, проверку независимых ручных примеров и выдачи для запросов без даты.

```sh
.venv/bin/python benchmark.py --k 1 5 10 --repeats 1 --output .cache/validation/public.json
.venv/bin/python tools/check_search_probes.py --output .cache/validation/probes.json
.venv/bin/python benchmark.py --queries tests/fixtures/queries_no_date.jsonl \
  --unjudged --repeats 1 --output .cache/validation/no-date.json
```

Чтобы прогнать новый размеченный корпус, указать один каталог со своим `documents.jsonl` в `./run.sh --data` и `benchmark.py --data`, передать нужные файлы через `--queries` и `--qrels`, а клиенту — URL соответствующего сервера. Сохранить версию кода и моделей, SHA-256 данных, оценки и ID выдачи по запросам, параметры замера и длительности. Текущий оценщик уже считает Recall, nDCG, MRR и задержки. Пустые и неразмеченные запросы он пропускает в среднем качества. Группы, подтверждённые пустые случаи, кандидаты первого этапа и эталоны RAG — дополнительная разметка и расчёты по описанному протоколу. [Параметры запуска](README.md#другой-корпус-или-новые-тесты) · [Код оценки](benchmark.py)

### Когда RAG действительно отвечает на вопрос

Искомое письмо может стоять первым, а ответ из него всё равно может оказаться неполным. В пилоте VK исходная версия правильно назвала один из пяти фактовых ответов. В двух случаях она отказала, в двух других показала выдержки без запрошенной информации. Все показанные выдержки имели источники. На вопрос об операторе нашлось второе допустимое письмо с другим человеком. Учёт второго письма оставляет оценку сравнения поиска прежней, поскольку обе версии поставили эти письма на первые два места. [Проверка ответов по оригиналам](results/validation_pilot/rag-review.json)

После этого использовали три вопроса открытой части для исправления составных запросов. В «Найди заказ. Сколько он стоил?» последняя фраза должна доходить до модели как вопрос о цене. Для инструкции вместе с вопросом о количестве сервер может выбрать два фрагмента и сослаться на одно письмо. Если единственная подходящая сумма приведена без валюты, проверяется дословная выдержка. [Изменения в генераторе](mailsearch/generation.py) · [Проверки на вымышленных письмах](tests/test_rag_question_intent.py)

| Набор. Полный ответ и корректные ссылки | Исходный MVP | Новый поиск, прежний RAG `7897913` | Новый поиск и RAG `ec0edc9` |
| --- | ---: | ---: | ---: |
| Шесть регрессионных вопросов о суммах, сроках и статусе | 5/6 | 6/6 | 6/6 |
| Пять адресных вопросов пилота, три использованы для исправления | 1/5 | 1/5 | 4/5 |
| Шесть вопросов о новых событиях, для которых в письмах есть ответы | 2/6 | 2/6 | 2/6 |

Для предпоследней строки агент заранее выбрал девять разных событий и зафиксировал семь фактов. В первом слепом прогоне широкое изменение инструкции модели снизило число ответов с подтверждением с 2/6 до 1/6. После возврата прежней инструкции для простых вопросов повтор дал 2/6. Для трёх вопросов с недостатком сведений исходный MVP явно отказал в 2/3 случаев, новый поиск с обеими версиями генератора — в 3/3. В исходных четырёх регрессионных примерах отказ сохранился в 4/4, в пилоте — в 1/2. Исправление составных вопросов не закрывает случаи, где в подходящем письме есть несколько сумм, участников или стадий события. Зафиксировали авторскую версию `fade3eae`, исходные русские вопросы и все 56 952 пассажа из 9 105 страниц Википедии. Оценивали 1 694 тестовых вопроса с 2 847 подтверждёнными парами.
