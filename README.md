# Конверт · умный поиск в почте

Локальный прототип для кейса VK на хакатоне Студсовета ФПМИ. В интерфейсе можно открыть любой из 12 учебных ящиков, найти письма обычным русским запросом и получить ответ с переходом к оригиналу. В этом файле собраны контекст задачи, инженерные решения и воспроизводимые проверки.

## Материалы для работы над поиском

- [Аудит корпуса и публичной разметки](docs/vk_mail_search_analysis.md) содержит статистику писем, примеры ошибок, ограничения dev и код для воспроизведения базового эксперимента.
- [Методы поиска и план экспериментов](docs/vk_mail_search_methods.md) описывает кандидатов для retrieval и reranking, измерение p99 и варианты архитектуры. Результаты текущей реализации приведены ниже в разделе «Проверка».

## Запуск

Запустите сервис из корня проекта на macOS или Linux.

```sh
./run.sh
```

Откройте [почту на localhost](http://localhost:8765/). Скрипт использует `uv` или установленный Python 3.12, ставит зависимости в `.venv` и проверяет наличие моделей. На чистой машине понадобится интернет для установки библиотек и загрузки около 3,6 ГБ весов с Hugging Face. Индекс писем строится автоматически. На этом компьютере модели и индекс уже подготовлены. Сервер привязан к `127.0.0.1`. Для другого порта используйте `./run.sh --port 8766`, для остановки в терминале нажмите Ctrl+C.

В подготовленном окружении данные можно проверить отдельно и запустить сервер с локальными весами.

```sh
.venv/bin/python -m mailsearch.prepare --offline
.venv/bin/python -m mailsearch
```

### Подключение своей почты

В [демо](https://ssd2008.github.io/HackFPMI-demo/) или на [localhost](http://localhost:8766/) нажмите **«Подключить свою почту»**. Выберите Gmail или Яндекс Почту, введите адрес ящика и созданный у провайдера пароль приложения. Для Google нужна двухэтапная аутентификация и возможность создавать пароли приложений. Для Яндекса разрешите IMAP в настройках почтовых программ и создайте пароль приложения для почты. [Справка Google](https://support.google.com/accounts/answer/185833?hl=ru) · [Справка Яндекса](https://yandex.ru/support/yandex-360/customers/mail/ru/mail-clients/others)

Сервис читает до 500 последних писем из папки «Входящие» по IMAP через TLS и показывает новые письма первыми. Переход во входящие открывает поиск и просмотр оригиналов. Пока сессия активна, сервис сверяет изменения примерно раз в пять минут. Для немедленного обновления нажмите **«Синхронизировать»**. У больших писем сервис читает первые 256 КиБ сообщения и индексирует до 16 384 знаков текста. Интерфейс отмечает письма, загруженные частично.

У каждого посетителя своя сессия. Пароль приложения, письма и их поисковый индекс хранятся в оперативной памяти сервера. Нажатие **«Выйти и отключить почту»** завершает доступ и очищает данные сессии. Сессия также заканчивается через час или при перезапуске сервера. В браузере временно хранится ключ доступа к сессии. Для нового подключения после выхода снова потребуется пароль приложения.

### Настройка Mac один раз

На Mac с Apple Silicon и macOS 14+ нужен Homebrew, доступ к приватному `HackFPMI` и право Write в `HackFPMI-demo`. Для коммитов Pages настройте в Git имя и подтверждённый на GitHub адрес почты.

```sh
brew install gh uv tmux cloudflared
gh auth login --hostname github.com --git-protocol https
gh auth setup-git
git clone https://github.com/ssd2008/HackFPMI.git ~/HackFPMI-preview
tmux new-session -d -s hackfpmi-tunnel 'cloudflared tunnel --url http://127.0.0.1:8765'
tmux capture-pane -pt hackfpmi-tunnel -S -80
```

`tmux` (terminal multiplexer) держит процессы в отдельных сессиях после закрытия терминала. Возьмите из вывода `cloudflared` HTTPS-адрес и подставьте его при первом деплое. Если порт 8765 занимает старый ручной запуск, сначала остановите его.

```sh
~/HackFPMI-preview/scripts/deploy_preview.sh --api-origin https://ВАШ-АДРЕС.trycloudflare.com
```

На первом запуске будут скачаны модели и построен индекс. Журнал сервера находится в `~/HackFPMI-preview/.cache/preview-backend.log`.

### После изменений в `main`

```sh
~/HackFPMI-preview/scripts/deploy_preview.sh
```

Команда подтягивает `main`, при изменении бэкенда перезапускает API и дожидается ответа от него. Идентификаторы должны совпасть после завершения [деплоя Pages](https://github.com/ssd2008/HackFPMI-demo/actions). Откройте демо, выполните поиск и откройте письмо. После перезапуска Quick Tunnel получит новый адрес. Повторите команду с `--api-origin`, чтобы его обновить. Держите Mac включённым и подключённым к сети. Для стабильного адреса можно использовать [именованный Cloudflare Tunnel](https://developers.cloudflare.com/tunnel/get-started/).

## Что требуют организаторы

Основной результат — веб-сервис для просмотра почты и поиска, который позволяет найти нужное письмо без знания точной формулировки. Команда выбирает сценарии и обосновывает их. Для защиты нужны исходный код, инструкция запуска, рабочая демонстрация и объяснение решения. Localhost подходит. Публикация в интернете даёт дополнительный балл. Ответы по письмам выбраны как дополнительная функция по запросу пользователя. [Исходная постановка](data/vk-mail-search.pdf)

Требование к скорости — **p99 строго меньше 1000 мс** от получения запроса сервером до готовой выдачи. Время включает разбор запроса, извлечение кандидатов и ранжирование. Сеть до браузера и отрисовка исключены. За превышение предусмотрен штраф. На этапах поиска и повторного ранжирования также предусмотрен штраф за использование модельных API или моделей более 3 млрд параметров. Ограничение относится к поисковому движку. Окончательные правила нагрузки, прогрева, кэширования и официальные метрики определяют организаторы. [Условие](data/vk-mail-search.pdf)

Прототип показывает срез ящика на выбранную дату. Письмо с известной датой доступно начиная с этого дня. У 433 писем дата получения отсутствует. Такие письма доступны при обычном поиске, во входящих стоят после датированных писем и исключаются из поиска за конкретный период. Даты внутри текста могут описывать доставку, платёж или другое событие. Периоды в поисковом запросе прототип трактует как периоды **получения**. Все даты синтетические, поэтому стартовая дата соответствует последнему письму выбранного ящика.

## Как устроен поиск и RAG

1. **Область поиска.** Выбираем письма нужного `synthetic_user`, полученные к дате запроса. Разбираем «вчера», «позавчера», явные даты, диапазоны и распространённые периоды. При запросе без темы, например «письма за вчера», сортируем по дате. Для ID письма, кода заказа и адреса отправителя поддерживается точное совпадение.
2. **Лексический поиск.** Русский стеммер приводит словоформы к общей основе. BM25-подобная оценка учитывает редкость слов, длину письма, совпадения в теме и долю совпавших терминов. У часто встречающихся понятий есть общие признаки для синонимов. Непрозрачные коды сохраняются в отдельности.
3. **Смысловой поиск.** Локальная `intfloat/multilingual-e5-small` (117,65 млн параметров) кодирует запросы и письма в нормированные векторы из 384 чисел. Текст для E5 очищается от длинных кодов и ссылок. Энкодер видит до 120 токенов. Лексический индекс охватывает полный текст, включая хвосты длинных писем. Заранее рассчитанная матрица эмбеддингов занимает около 24 МиБ и переиспользуется между запусками.
4. **Выдача.** Для доступных кандидатов объединяем лексическую оценку и нормированную косинусную близость с весами 0,55 и 0,45. Слабые совпадения отсекаются. Поиск по смыслу выполняется локально на CPU. Для единственного точного совпадения по идентификатору достаточно проверки области видимости и самого идентификатора.
5. **Ответ.** По отдельному запросу сервер повторяет поиск в том же срезе ящика и передаёт до трёх подходящих писем из первых пяти в локальную `Qwen2.5-1.5B-Instruct`. Модель получает отдельный фрагмент на письмо. Сервер проверяет сгенерированную фразу по тексту и привязывает её к исходному `doc_id`. Есть проверки чисел, кодов и статусов. Если ответ не проходит проверку или модель занята, интерфейс может показать явно помеченные дословные выдержки. При недостатке сведений отображается соответствующее сообщение. Модель загружается при первом запросе ответа. Пользователь получает поисковую выдачу до генерации.

Сервис читает только корпус писем. Подсказки в интерфейсе строятся из текстов ящика. Публичные запросы и разметку читает отдельный скрипт оценки. Закреплённые ревизии обеих моделей находятся в [mailsearch/__init__.py](mailsearch/__init__.py).

## Проверка

Эти команды запускаются во втором терминале, пока почта открыта на порту 8765.

```sh
.venv/bin/python benchmark.py --k 1 5 10 --repeats 3 --output results/public_dev.json
.venv/bin/python benchmark.py --k 10 --repeats 3 --concurrency 8 --output results/public_dev_8_clients.json
.venv/bin/python -m unittest discover -s tests -v
```

`benchmark.py` отправляет запросы по HTTP на тот же `/api/search`, что и браузер. Скрипт проверяет связи разметки, уникальность выдачи, владельца каждого письма и его доступность на дату запроса. Качество считается по первому проходу. Recall и nDCG усредняются по 99 запросам, MRR — по 42 запросам с одним релевантным письмом. При подсчёте метрик письма без разметки получают оценку 0.

Для измерения времени используется уже подготовленный сервер. Порядок запросов перемешивается воспроизводимо. В каждом из трёх проходов по 99 запросов. Серверный таймер включает чтение тела HTTP-запроса приложением, обработку, ожидание свободного обработчика и сериализацию выдачи. Клиент отдельно измеряет полный HTTP-запрос через loopback. p99 считается методом ближайшего ранга. Готовые выдачи между запросами не кэшируются. Качество ответов генератора проверяется на отдельных примерах с оригиналами писем.

### Результаты на публичном наборе

Измерено 21 ноября 2026 года на Apple M5 Pro, 48 ГиБ памяти, Python 3.12.13. Каждая выдача проверена на соответствие ящику и дате. [Выдача и метрики по каждому запросу](results/public_dev.json)

| K | Recall@K | nDCG@K | MRR@K · 42 запроса с одним письмом |
| ---: | ---: | ---: | ---: |
| 1 | 0,554920 | 0,979798 | 1,000000 |
| 5 | 0,859615 | 0,991076 | 1,000000 |
| 10 | 0,937564 | 0,992764 | 1,000000 |

Во всех 42 запросах с единственным релевантным письмом оно оказалось на первом месте. Для 15 из 99 запросов размечено больше десяти писем, максимум — 65. Из-за ограничения длины выдачи теоретический максимум среднего Recall@10 составляет 0,937564 с округлением до шести знаков. Этого значения движок достиг на публичном наборе.

Интеграционные проверки охватывают обращение к чужому и будущему письму по прямому ID, недатированное письмо, отсутствующий заказ и подтверждение суммы в источнике RAG. В браузере проверены переключение ящика, страницы входящих, выбор даты, запуск примера и открытие оригинала по ссылке из ответа.

### Программный доступ

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/mailboxes` | Список ящиков, даты и примеры. |
| `GET /api/inbox?mailbox=…&date=YYYY-MM-DD&offset=0&limit=25` | Страница входящих на заданный день. |
| `GET /api/actions?mailbox=…&date=YYYY-MM-DD&offset=0&limit=25` | Письма с просьбами, найденными по правилам. У каждого результата есть `evidence` и опциональные `deadline` и `deadline_time`. Поле `urgent` содержит до трёх ближайших сроков на дату среза и следующий день. |
| `POST /api/actions` | Тот же список с ручными отметками. JSON содержит `mailbox`, `date`, `offset`, `limit` и массив `marked` из ID писем. |
| `GET /api/reminder-candidates?mailbox=…&date=YYYY-MM-DD` | ID и темы писем с просьбами из того же среза. |
| `POST /api/assistant` | JSON с полями `mailbox`, `date`, `query`. Возвращает `kind` (`events`, `mail` или `watch`), `items` и при необходимости `message`. |
| `POST /api/assistant/watch` | Принимает те же поля плюс `after` (включительно) и `seen` (ID уже известных писем). Возвращает `items` и `matched_ids`. |
| `GET /api/mail/{doc_id}?mailbox=…&date=YYYY-MM-DD` | Оригинал письма. Недоступное по ящику или дате письмо даёт 404. |
| `POST /api/search` | JSON с полями `mailbox`, `date`, `query`, `limit` от 1 до 100. В ответе ранжированный список `items`. |
| `POST /api/answer` | Те же ящик, дата и запрос. В ответе `answer`, упорядоченные `sources`, а также `mode` со значением `generative`, `extractive` или `no_evidence`. |


Ручные отметки, расписание напоминаний и отслеживания хранятся в текущем браузере. Автонапоминания планируются на 19:00 при первом обнаружении письма, если это время ещё впереди, и на 12:00 следующего дня по местному времени браузера. Выбранное вручную время заменяет оба события.
