
# Умный поиск в Почте VK
## Анализ задачи, существующие методы и идеи реализации

Дата: 21 ноября 2026 года

## 1. Постановка задачи

Необходимо разработать веб-сервис для просмотра анонимизированных писем и интеллектуального поиска по ним.

Главная проблема: обычный полнотекстовый поиск не позволяет найти письмо, если пользователь не помнит точные слова из него.

Например, пользователь вводит:

> Найди письмо, где мне обещали вернуть деньги за отменённую поездку.

Система должна находить релевантное письмо, даже если в нём написано:

> Возврат стоимости бронирования будет произведён в течение десяти рабочих дней.

### Ограничения

- p99 времени поиска строго меньше 1 секунды.
- Время включает обработку запроса, retrieval и reranking.
- Модели больше 3 млрд параметров на этих этапах приводят к штрафу.
- Использование внешних API моделей для поиска также штрафуется.
- Качество оценивается на публичном и приватном бенчмарках.
- Метрики и формат бенчмарков пока не объявлены.
- Требуется работающий веб-интерфейс и репозиторий.
- За интернет-развёртывание предусмотрен дополнительный балл.

Важно: использование больших моделей и API не полностью запрещено. Согласно заданию, оно снижает оценку только при применении на этапах retrieval и reranking.

## 2. Основной вывод

Наиболее перспективная стартовая архитектура:

BM25 + Dense Retrieval + RRF + Cross-Encoder Reranking

Она объединяет:

1. Точный лексический поиск.
2. Семантический поиск.
3. Объединение кандидатов.
4. Точное повторное ранжирование.
5. Дополнительную обработку дат, отправителей и сущностей.

Это не гарантированный победитель на неизвестном корпусе. Однако такая архитектура является сильной отправной точкой, которую можно улучшать экспериментально.

## 3. Проверенные методы

### 3.1. BM25

BM25 представляет документы через совпадения терминов и статистические веса.

Преимущества:

- Очень высокая скорость.
- Хорошо ищет имена, номера, адреса и идентификаторы.
- Не требует нейросетевого инференса.
- Подходит для первого этапа retrieval.

Недостатки:

- Плохо понимает синонимы.
- Не распознаёт смысловые перефразировки.
- Зависит от нормализации текста.

Для русского языка полезно экспериментировать с лемматизацией, стеммингом и отдельным сохранением исходных токенов.

Рекомендация: обязательно использовать BM25 как baseline и как компонент гибридного поиска.

### 3.2. Dense Retrieval

Текст запроса и письма преобразуется в векторы с помощью нейросетевого энкодера.

Релевантность оценивается по близости векторов, например cosine similarity.

Преимущества:

- Поиск по смыслу.
- Работа с синонимами.
- Устойчивость к перефразировкам.
- Возможность мультиязычного поиска.

Недостатки:

- Иногда теряет точные идентификаторы.
- Может путать семантически похожие, но фактически разные письма.
- Требует вычисления эмбеддинга запроса.

Для ускорения используются FAISS и HNSW.

### 3.3. Hybrid Search

BM25 и Dense Retrieval выполняются независимо.

Каждый возвращает список кандидатов.

Затем результаты объединяются.

Такой подход позволяет одновременно находить:

- Письма с точными совпадениями.
- Письма с близким смыслом.
- Письма с редкими именами и кодами.
- Письма с другими формулировками.

Это один из наиболее практически обоснованных методов для данной задачи.

### 3.4. Reciprocal Rank Fusion

RRF объединяет результаты нескольких поисковых систем по их позициям в рейтингах.

Формула:

RRF(d) = sum_i 1 / (k + rank_i(d))

Обычно стартуют с k = 60.

Главное преимущество: не требуется приводить BM25 и cosine similarity к общей шкале.

Начальные параметры для экспериментов:

- BM25: top-100.
- Dense: top-100.
- RRF: k = 60.
- Итоговые кандидаты: top-50.

Все значения требуют проверки на корпусе организаторов.

### 3.5. Cross-Encoder Reranking

Cross-Encoder получает запрос и письмо одновременно.

В отличие от bi-encoder, модель анализирует взаимодействие токенов двух текстов.

Это часто повышает точность ранжирования.

Недостаток: высокая вычислительная стоимость.

Поэтому Cross-Encoder следует применять только к небольшому количеству кандидатов.

Стартовая конфигурация:

- Retrieval: 100 кандидатов на каждый метод.
- Fusion: 50 кандидатов.
- Reranking: 20-50 кандидатов.
- Выдача: top-10.

Размер reranking-пула должен определяться по качеству и p99.

### 3.6. SPLADE

SPLADE использует нейросетевую модель для построения разреженных представлений документов.

Она способна расширять набор терминов, сохраняя возможность поиска через инвертированный индекс.

Преимущества:

- Семантическое расширение терминов.
- Совместимость с sparse-поиском.
- Хорошие результаты в исследованиях информационного поиска.

Недостатки:

- Дополнительная сложность.
- Необходимость подобрать модель под русский язык.
- Возможные расходы на индексацию.

SPLADE стоит рассматривать как эксперимент второго приоритета, а не обязательный компонент первой версии.

### 3.7. Learning-to-Rank

Можно обучить модель ранжирования, например LambdaMART, на признаках:

- BM25 score.
- Dense similarity.
- Cross-Encoder score.
- Совпадение темы.
- Совпадение отправителя.
- Временная близость.
- Совпадение сущностей.
- Наличие вложений.

Преимущество: модель может учитывать структуру электронной почты.

Недостаток: нужны достаточно качественные размеченные данные.

Без надёжной разметки LTR может переобучиться на публичном бенчмарке.

## 4. Открытые модели

Для сравнения стоит рассмотреть:

| Модель | Назначение |
|---|---|
| multilingual MiniLM | Быстрые мультиязычные эмбеддинги |
| multilingual E5 | Семантический retrieval |
| ai-forever/sbert_large_nlu_ru | Русскоязычные эмбеддинги |
| Multilingual SBERT | Мультиязычные представления |
| Cross-Encoder на русских retrieval-данных | Reranking |

Не стоит использовать обычный mBERT или XLM-R без соответствующего обучения для семантического поиска: их стандартные представления предложений могут быть существенно хуже специализированных моделей.

Конкретную модель следует выбирать по двум параметрам:

1. Качество на русскоязычных поисковых данных.
2. Скорость на доступном оборудовании.

Нельзя выбирать модель только по общему лидерборду.

## 5. Архитектура сервиса

### 5.1. Offline-индексация

Для каждого письма:

1. Извлечь заголовок и тело.
2. Очистить HTML.
3. Сохранить отправителя и получателей.
4. Нормализовать дату.
5. Извлечь идентификаторы и сущности.
6. Построить BM25-индекс.
7. Вычислить эмбеддинг.
8. Добавить в векторный индекс.
9. Сохранить связи переписки.

Индексация выполняется заранее.

### 5.2. Online-поиск

Пользовательский запрос
    |
    v
Нормализация и анализ
    |
    +---- BM25 Retrieval
    |
    +---- Dense Retrieval
    |
    v
RRF Fusion
    |
    v
Metadata-aware Ranking
    |
    v
Cross-Encoder Reranking
    |
    v
Top-10 результатов

BM25 и Dense Retrieval желательно запускать параллельно.

### 5.3. Технологический стек

Возможная конфигурация:

Backend:
- Python
- FastAPI

Лексический поиск:
- Elasticsearch / OpenSearch

Векторный поиск:
- FAISS / hnswlib

Модели:
- SentenceTransformers
- PyTorch / ONNX Runtime

Frontend:
- React
- TypeScript

Deployment:
- Docker
- Облачный сервер

Это пример реализации, а не обязательный набор технологий.

## 6. Оптимизация p99

Ограничение p99 < 1 секунды означает, что быстрым должен быть не только средний запрос, но и почти все запросы.

### 6.1. Пример целевого бюджета

| Этап | Целевое время |
|---|---:|
| Обработка запроса | 20 мс |
| Query embedding | 80 мс |
| Retrieval и fusion | 100 мс |
| Reranking | 400 мс |
| Подготовка ответа | 30 мс |
| Резерв | 370 мс |

Это инженерные ориентиры, не измеренные результаты.

Поскольку некоторые операции выполняются параллельно, суммарное время следует измерять непосредственно на сервере.

### 6.2. Оптимизации

- Предварительное вычисление эмбеддингов писем.
- Хранение индексов в оперативной памяти, если позволяет объём.
- FP16 или INT8 для нейросетевых моделей.
- Батчинг reranking.
- ONNX Runtime для ускорения инференса.
- Ограничение длины входа Cross-Encoder.
- Кэширование популярных запросов.
- Прогрев моделей.
- Параллельный retrieval.
- Контроль количества кандидатов.

Важно: нельзя полагаться только на кэш. Правила прогрева и кэширования организаторы ещё не определили.

Асинхронное обновление выдачи после первого ответа не заменяет полноценный reranking в измеряемом поисковом ответе.

## 7. Особенности поиска по электронной почте

Письма отличаются от обычных документов.

Они содержат:

- Отправителей.
- Получателей.
- Темы.
- Даты.
- Цепочки переписки.
- Пересылаемые сообщения.
- Подписи.
- Цитаты предыдущих писем.
- Вложения.
- Номера заказов и документов.

Эти признаки нужно использовать отдельно от общей семантики.

### 7.1. Поиск по полям

Предлагается хранить отдельные поля:

- subject
- body
- sender
- recipients
- timestamp
- thread_id
- attachment_names

Индексировать их с разными весами.

Например, совпадение редкого термина в теме может быть информативнее совпадения в длинной подписи.

### 7.2. Удаление шума

Следует экспериментировать с:

- Удалением HTML-разметки.
- Выделением основного текста.
- Удалением повторяющихся подписей.
- Отделением цитируемых сообщений.
- Удалением типовых рекламных блоков.

Но нельзя безусловно выбрасывать цитаты: иногда именно они содержат искомую информацию.

## 8. Собственные идеи

Ниже приведены гипотезы, которые нужно проверять экспериментально.

### Идея 1. Поиск по намерению пользователя

Разделить запросы на категории:

- Найти конкретное письмо.
- Найти подтверждение действия.
- Найти договорённость.
- Найти информацию о платеже.
- Найти письмо от человека.
- Найти письмо за период.

Например:

> Где мне обещали прислать документы?

Это не просто тематический запрос о документах.

Пользователь ищет сообщение с определённым речевым действием: обещанием.

Можно извлекать из писем признаки:

- Обещание.
- Подтверждение.
- Отказ.
- Запрос.
- Напоминание.
- Согласование.

Затем учитывать совпадение этих признаков при ранжировании.

### Идея 2. Поиск по событиям

Представлять письмо не только как текст, но и как набор событий.

Пример:

> Ваш заказ отправлен 15 мая.

Структура:

event_type: shipment
object: order
status: sent
date: 15 May

Тогда запрос:

> Когда мне отправили покупку?

можно сопоставлять с событием отправки, даже если в письме нет слова «покупка».

Такая система особенно перспективна для транзакционных писем.

### Идея 3. Двухуровневая индексация

Создать два представления каждого письма:

1. Полный текст.
2. Краткое семантическое описание.

Например:

Оригинал:
> В соответствии с ранее согласованными условиями денежные средства будут перечислены...

Описание:
> Уведомление о возврате денег.

Поиск выполнять по обоим представлениям.

Генерацию описаний можно проводить заранее, но необходимо проверить допустимость выбранного способа в рамках регламента.

### Идея 4. Граф переписки

Построить граф:

- Письмо.
- Отправитель.
- Получатель.
- Тема.
- Цепочка.
- Событие.

Если пользователь ищет:

> Ответ на мою просьбу перенести встречу.

можно найти письмо с просьбой, а затем проверить ответы в той же цепочке.

Это потенциально решает задачи, которые плохо выражаются через независимые эмбеддинги отдельных писем.

### Идея 5. Адаптивный поиск

Не все запросы требуют одинаковой обработки.

Примеры:

`AB-123456`
- Преимущество у точного поиска.

`письмо про возврат денег`
- Преимущество у семантического поиска.

`от Ивана в прошлом месяце`
- Преимущество у метаданных.

Можно обучить небольшой классификатор типа запроса и адаптивно менять веса компонентов.

Однако адаптивный поиск не должен необоснованно отключать полезные retrieval-ветки.

### Идея 6. Контрастивные негативные примеры

Для дообучения retriever особенно полезны сложные отрицательные примеры.

Например:

Запрос:
> Подтверждение возврата денег за билет.

Положительный пример:
> Возврат стоимости билета выполнен.

Сложный отрицательный:
> Заявка на возврат билета зарегистрирована.

Второе письмо тематически очень близко, но не подтверждает завершённый возврат.

Такие примеры позволяют обучать модель различать фактическое состояние события.

### Идея 7. Разделение фактов и упоминаний

Письмо может упоминать событие, не подтверждая его.

Пример:

> Мы рассмотрим возможность возврата средств.

Это не то же самое, что:

> Средства возвращены.

Можно извлекать:

- Тип события.
- Статус.
- Время.
- Отрицание.
- Модальность.

Это особенно полезно для запросов о выполненных действиях.

## 9. План экспериментов

### Этап A. Baseline

Реализовать:

- BM25.
- Простой интерфейс.
- Оценку качества.
- Замер latency.

### Этап B. Dense Retrieval

Сравнить несколько моделей эмбеддингов.

Измерить:

- Recall@10.
- Recall@50.
- Recall@100.
- MRR@10.
- nDCG@10.
- p50 и p99.

### Этап C. Hybrid

Сравнить:

- BM25.
- Dense.
- BM25 + Dense + RRF.

Подобрать количество кандидатов и параметры fusion.

### Этап D. Reranking

Проверить:

- Без reranker.
- Reranker top-10.
- Reranker top-20.
- Reranker top-50.

Найти оптимальное соотношение качества и скорости.

### Этап E. Email-specific признаки

Добавлять по одному:

- Даты.
- Отправители.
- Темы.
- События.
- Цепочки переписки.
- Дополнительные семантические описания.

Каждое изменение должно сопровождаться ablation study.

## 10. Риски

### 10.1. Переобучение на публичном бенчмарке

Публичный набор может не отражать распределение приватных запросов.

Нельзя настраивать систему исключительно под известные формулировки.

### 10.2. Слишком тяжёлый reranker

Даже качественная модель бесполезна, если p99 превышает установленный предел и приводит к штрафу.

### 10.3. Неправильная обработка длинных писем

При усечении текста можно потерять релевантный фрагмент.

Возможное решение: индексировать несколько фрагментов письма и агрегировать их оценки.

### 10.4. Ошибки в метаданных

Дата, отправитель и цепочка переписки должны обрабатываться аккуратно.

Особенно важно различать дату самого письма и даты событий, упомянутых внутри текста.

### 10.5. Синтетические данные

Автоматически сгенерированные запросы могут оказаться слишком похожими на текст писем.

Для проверки обобщения нужны независимые перефразировки и сложные отрицательные примеры.

## 13. Практическая рекомендация

Начинать с гибридной архитектуры:

BM25 + Dense + RRF.

Затем подключать небольшой Cross-Encoder.

После этого работать над специфическими особенностями электронной почты:

- Событиями.
- Датами.
- Отправителями.
- Цепочками.
- Статусами действий.

Сложные методы вроде SPLADE и графового поиска стоит добавлять только при наличии измеримого прироста.

Главная стратегия: сначала построить сильный и быстрый baseline, затем улучшать его на основе экспериментов.

## 15. Заключение

Успешное решение задачи требует не одной большой нейросети, а хорошо организованной поисковой системы.

Наиболее обоснованный подход:

1. Надёжный лексический retrieval.
2. Семантический retrieval.
3. Объединение кандидатов.
4. Быстрое и точное reranking.
5. Использование структуры писем.
6. Систематическая оценка качества.
7. Контроль p99.

Наиболее интересные экспериментальные направления:

- Поиск по намерению пользователя.
- Поиск по событиям и их статусам.
- Семантические описания писем.
- Контрастивное обучение на сложных отрицательных примерах.
- Использование графа переписки.

Их преимущество пока является гипотезой. Проверять его нужно на реальных данных и независимой тестовой выборке.
