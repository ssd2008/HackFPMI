# Датасеты для «Умного поиска в Почте»

## Бенчмарк хакатона

По README организаторов, корпус содержит 16 376 псевдонимизированных писем. Публичная разметка включает 99 запросов и 565 пар «запрос, релевантное письмо». Тексты и даты в README описаны как синтетические. Финальная оценка проходит на закрытом бенчмарке. Файлы бенчмарка уже лежат в [`data/`](data/).

| Файл | Поля |
| --- | --- |
| `documents.jsonl` | `doc_id`, `synthetic_user`, `doc`, `doc_dt` |
| `queries_dev.jsonl` | `query_id`, `synthetic_user`, `query`, `query_date` |
| `qrels_dev.jsonl` | `query_id`, `doc_id`, `relevance` |
| `manifest.json` | Количество строк и контрольные суммы SHA-256 |

- Поиск ограничен ящиком из `synthetic_user`. По README проекта, 99 публичных запросов относятся к семи ящикам. В интерфейсе доступно 12 ящиков.
- Относительные даты считаются от `query_date`. Письмо с известной `doc_dt` позже даты запроса исключается. Для 433 писем дата неизвестна. Текущий движок показывает их при обычном поиске и исключает при запросе за конкретный период.
- До экспериментов стоит сверить SHA-256 файлов, проверить ссылки из qrels, ящики, даты и дубликаты пар. Версии разметки нужно сверять с соответствующими манифестами.
- Пересечение документов между запросами допустимо для поиска по общему индексу. При локальной валидации после дообучения важно держать похожие запросы в одном фолде, чтобы близкие формулировки не попали одновременно в обучение и оценку.
- Неразмеченные пары получают нулевую оценку при расчёте метрик, хотя отдельные письма могут оказаться релевантными при ручной проверке. Шаблоны синтетических текстов и близкие дубликаты могут завышать локальную оценку.

## Что показал аудит публичных данных

- Все 99 запросов ограничены одним днём. В 26 случаях написано «вчера», в 73 дата указана явно. Во всех 99 случаях запрошен предыдущий день. После нормализации вводной фразы и даты остаются 12 тематических формулировок.
- Для 49 из 99 запросов все письма нужного ящика за запрошенный день совпадают с полной разметкой. По остальным 50 запросам полезно смотреть метрики отдельно, чтобы измерить вклад ранжирования.
- У 15 запросов больше десяти положительных документов. Максимальный средний Recall@10 при этом равен 0,937564. У 42 запросов ровно одно размеченное письмо, а запросов без положительных документов в dev нет.
- Из 180 писем с темой «Покупатель отменил заказ» 179 не имеют даты получения. Для поиска без временного ограничения сохраняй такие письма в кандидатах. При группировке результатов учитывай, что синтетический номер может повторяться у разных объектов.
- Для ручной оценки добавь запросы без даты, за несколько дней, без ответа и с различием между фактом, разрешением и условием. Отдельно проверяй, что дата события в тексте не подменяет дату получения письма.

В диагностическом эксперименте из рабочего анализа получены следующие значения на публичном наборе. Это отдельные простые методы, поэтому результаты текущего сервиса приведены в [README проекта](README.md).

| Метод | Recall@10 | nDCG@10 |
| --- | ---: | ---: |
| Фильтр дня, сортировка по `doc_id` | 0,655863 | 0,663316 |
| BM25 с фильтром дня | 0,770834 | 0,762214 |
| Символьный TF-IDF с фильтром дня | 0,929218 | 0,978024 |

## Порядок экспериментов

1. Сравнить BM25 и векторный поиск на одном наборе допустимых писем. Измерить Recall@K, nDCG@K и MRR@K для запросов с одним размеченным письмом.
2. Проверить гибридную выдачу и реранкинг до 100 кандидатов. Сравнить прирост качества с ростом задержки.
3. Если нужен тюнинг, начать с размеченных русскоязычных разделов mMARCO, MIRACL или Mr. TyDi. Проверить, переносится ли выигрыш с веб-текстов на письма. Для адаптации к почте можно сгенерировать независимые запросы к письмам и вручную проверить часть пар.
4. Если публичные запросы используются при обучении, оценивать качество на отложенных фолдах по группам похожих запросов. Если хватает внешнего обучения, сохранить публичный набор для локальной оценки.
5. Измерить p99 полного запроса, включая фильтрацию по ящику и дате, извлечение кандидатов и реранкинг. Требование бэкенда составляет строго менее 1 секунды. Для поиска и реранкинга учитывать ограничение в 3 млрд параметров и штраф за вызов модельных API. См. [постановку задачи](data/vk-mail-search.pdf).
